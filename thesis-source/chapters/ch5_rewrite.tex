\chapter{Robot-Side Implementation}\label{chap:robot_side_rewrite}

The robot-side client is the part of the system that turns the server architecture from Chapter~\ref{chap:server_side_rewrite} into an interaction with Pepper. It runs in Pepper's NAOqi environment, listens through QiChat, moves the head during scans, captures camera images, collects robot metadata, calls the server, speaks answers, and updates the tablet.

\section{Runtime Structure}\label{sec:client-runtime-structure}

\caption{Robot-side client architecture. QiChat calls the PepperGroundedClient service's methods. The service delegates long actions to the turn manager, which collects robot context, builds metadata, calls the server transport, and updates speech, tablet output, local state, and dynamic dialogue concepts.}\label{fig:client-runtime-graph}
\end{figure}

Figure~\ref{fig:client-runtime-graph} shows the client as a NAOqi service boundary around smaller adapters. The main service is \texttt{PepperGroundedClient}. It exposes bound methods for quick look, scan, chat, object chat, cached answers, memory display, and reset. These methods are intentionally thin. They log the call, normalize small arguments, and delegate long-running work to the turn manager.

At startup, the service loads \texttt{client\_config.json} (containing setup information such as server url for detection and panorama detection, scan head degrees, etc.) and constructs the adapters. The camera adapter wraps \texttt{ALVideoDevice}; the pose adapter wraps \texttt{ALMotion}; the people, face, social, and sonar adapters read robot-native context from NAOqi services and \texttt{ALMemory}; the speech adapter wraps animated speech and text-to-speech; the dialog adapter updates ALDialog dynamic concepts; the tablet adapter opens the local tablet page; the server transport owns HTTP calls; and the session store keeps short-lived local state. In addition, the client code also support \texttt{FakeCameraAdapter} and \texttt{FakeTabletAdapter} usable for testing of unavailable services for virtual robot in Choregraphe, a software used for programming NAO and Pepper robots. This adapter structure is practical because it separates individual NAOqi services and makes it easier to manage each component. Moreover, the NAOqi services differ in availability and failure behavior so they need special treatment~\cite{softbank_python_sdk_2026}.

\section{QiChat Grammar}\label{sec:client-qichat}

The spoken interface is defined in English and Czech QiChat topic files.
The grammar handles bounded interaction control; it decides whether a user asked for a quick look, a full scan, a memory display, a reset, an object-specific question, or a cached suggested question. It also provides system description and introduction so that user can find out what Pepper can do.
The crucial point is the LLMs do not replace this layer. QiChat is the only way user can interact with the service, and consequently the server. Each rule maps the user's intent to a service method, and the server-side LLM is used after the action and relevant parameters are known. This keeps the interaction controllable while still allowing grounded open-ended answers.

A \texttt{u:} rule matches an utterance and can call a Python method through \texttt{\^{}pCall}. The underscore before a dynamic concept captures the matched text into \texttt{\$1}. Dynamic concepts are the main link between server memory and speech recognition. After a perception update or a memory refresh, the client asks the server for a memory summary. It extracts object labels, attributes, relation predicates, and pregenerated questions, then writes them into the matching ALDialog memory concepts. The relation concept stores only the predicate names, they are to be used for recognition only. The full triples remain in server memory and do not get transported to the client apart from the tablet payload. Dynamic concepts bring the advantage of adjusting the QiChat grammar for the changing scene. If the server has just detected a chair and a bottle, the grammar can begin to recognize spoken questions about those labels without hard-coding them in the topic file.

\section{Turn Management}\label{sec:client-turn-management}

The operational center of the client is \texttt{TurnManager}. It implements quick look, full scan, general chat, object-focused chat, cached answering, memory display, visual refresh, and memory reset. A service method starts a turn by calling \texttt{\_start\_async}. The turn manager creates a turn identifier, checks whether the client is already busy, optionally speaks an acknowledgement, and starts a daemon thread for the actual work. This prevents long actions from blocking the NAOqi service method that QiChat or the tablet called.

%The busy flag is important because Pepper is a physical robot. Two turns should not move the head, capture images, speak, or update the tablet at the same time.
MAYBE REDUNDANT: The turn manager therefore accepts one long-running action at a time. If another action arrives while the robot is busy, the client speaks a localized busy fallback and rejects the new turn. Every guarded turn releases the busy state in a \texttt{finally} block, so a timeout or malformed server response does not leave the robot permanently locked.

\section{Visual Actions and Metadata}\label{sec:client-visual-actions}

The quick look action is optimized for a short answer. The client creates a frame identifier, captures one JPEG frame, collects robot context, builds metadata, and calls the server caption endpoint. The caption request also asks the server to run detection in the background. Pepper can therefore speak a quick description while the server runs the whole pipeline described in Section \ref{sec:server-perception-pipeline}.

The scan action is the wider observation path. The client records the original head pose, moves the head through configured yaw angles, waits for the head to settle, captures a frame at each pose, and restores the head at the end when configured. The current scan uses three yaw positions, \(-35^\circ\), \(0^\circ\), and \(35^\circ\); This can, however, be changed in the \texttt{client\_config.json}. The changes will apply after service restart or config reload. The captured frames can be sent as one panorama detection request or as individual detection requests. Panorama mode gives the server one broader image; sequential mode avoids stitching assumptions and treats every head pose as its own observation.

Each visual request contains a metadata payload in addition to the image. The camera adapter supplies image size, timestamp, JPEG bytes, and camera field of view. The pose adapter supplies head yaw, head pitch, and body yaw. The robot context collector adds visible people, social people, and sonar readings if available. The metadata builder combines these values with frame identifier, scan identifier, and capture mode. This is what lets the server relate image-space detections to Pepper's head pose, people perception and social cues.

People metadata comes from Pepper's own perception stack. The people adapter subscribes to \texttt{ALPeoplePerception} and reads visible person identifiers, yaw, pitch, and distance from \texttt{ALMemory}. The social adapter adds available signals from face characteristics, gaze analysis, engagement zones, sitting detection, and waving detection. The face adapter reads \texttt{FaceDetected} data and matches recognized faces to visible people by yaw and pitch. These signals are noisy, but they are valuable because they describe social facts that a normal object detector may miss~\cite{softbank_alspeechrecognition_2026}. This information is then turned into attributes on the server side, i.e. attribute \texttt{is\_sitting}, \texttt{is\_smiling}, \texttt{is\_1.5\_meters\_away}, etc.

\section{Server Communication}\label{sec:client-transport-state}

All server communication goes through \texttt{PepperServerTransport}. Image endpoints use multipart form uploads, while chat, reset, and question generation use JSON. The transport applies configured endpoint paths. It checks response shape before returning data to the turn manager, for example, caption responses must contain a caption, etc. Network timeouts, unavailable server responses, and malformed JSON are converted into client-specific errors, which the turn manager turns into spoken fallback messages, so the user is informed about the error.

General chat and object chat use the same server endpoint with different modes. For a general question, the client sends the sanitized user query, the current chat identifier, and the requested output language. For an object question, it also sends the recognized object label and the mode \texttt{object}. The server performs the actual object matching and context construction. The client does not decide which object instance was meant. It only passes the spoken label extracted by QiChat, so the context is constructed from all instances of the given label.

\chapter{Server-Side Implementation}\label{chap:server_side_rewrite}

Chapter~\ref{chap:system_architecture_rewrite} introduced the server as the external perception, memory, and language backend.
This chapter follows that boundary into implementation: the FastAPI runtime, public API, perception pipeline, memory update semantics, provider adapters, translation support, worker control, and dashboard.

\section{Runtime Structure and Application State}\label{sec:server-runtime-structure}

The public server process is a FastAPI application.
It exposes \texttt{/api/v1} for robot and dashboard calls, serves the dashboard under \texttt{/dashboard}, mounts static assets, and opens a WebSocket channel for live updates.
As required by the split in Section~\ref{sec:architecture-client-server}, Pepper never constructs detector, VLM, LLM, tracking, or memory objects directly.

\centering
\includegraphics[width=\linewidth]{pics/server_nicer.pdf}
\caption{Server runtime structure. Pepper and the dashboard communicate with the public FastAPI routes. Application services call a runtime adapter, which either uses an in-process perception pipeline or forwards the request to an internal worker process.}
\label{fig:server-runtime-structure}
\end{figure}

Figure~\ref{fig:server-runtime-structure} shows the main server components.
The central dependency root, \texttt{AppState}, stores the active configuration and version, runtime adapter, chat and caption services, conversation service, question-answer pool, and last published dashboard state.
Routes and orchestration services resolve their dependencies through this object, so configuration, runtime mode, prompts, providers, and memory access are coordinated in one place.

Two runtime modes share the same public contracts.
In-process mode keeps the perception pipeline inside the very same,  public FastAPI process. It is convenient for debugging or fast prototyping, but it is not suitable for production.
Worker mode starts a second internal FastAPI application and forwards heavy inference requests to it, which is preferred when detectors, caption models, embedding models, RelTR, or local VLMs allocate GPU memory that is difficult to release from a long-lived process. In this way, the worker can be killed and restarted on request or change of settings so as to release all GPU resources and reallocate them again.
The route layer calls a runtime adapter in both cases: the in-process adapter opens the uploaded image and calls the local pipeline, while the worker adapter serializes the same request to the internal worker API.

\section{Public API and Request Handling}\label{sec:server-public-api}

The public API is organized by robot-facing capabilities rather than by model internals.
Detection routes process visual observations, caption routes support the quick-look path from Section~\ref{sec:architecture-data-flow},\footnote{Caption routes can too start the full processing pipeline which is even used by the robot in order to get very fast answer, the caption, but at the same time trigger a full processing of the input in the background.} chat routes answer text questions from scene memory, and vision-chat routes send an image-question pair directly to a VLM.
Memory, configuration, and worker routes expose scene state, runtime settings, and process control.

The main detection request is a multipart image upload with optional JSON robot metadata.
The image can be resized before inference to control bandwidth and model cost.
The metadata contains values such as head yaw, head pitch, camera field of view, image size, frame identifier, scan identifier, battery state, and Pepper people-perception outputs.
At the API boundary, the metadata is parsed into Pydantic schemas so later pipeline stages receive normalized values rather than ad hoc dictionaries.

For scans, a request can contain several images with matching metadata.
The server either processes frames independently, preserving per-frame geometry, or stitches them into a panorama that gives the detector and VLM wider visual context.
Both modes are needed because Pepper scans by moving its head through several poses rather than by using a wide-angle camera.

Caption requests are optimized for quick look: the server receives one image and optional metadata, calls the configured caption service, and returns text with provider and model metadata.
The same request can trigger the full detection pipeline in the background, allowing Pepper to speak first while detections, scene graph relations, memory, and pregenerated questions are updated for later turns.

Chat requests are text-first but memory-grounded.
The route receives the user query, language information, conversation identifier, and optional object-focus label; it stores the original user message, builds model-facing history, asks the chat service for an answer, stores the response, and broadcasts it to the dashboard.
Keeping original and model-facing text separate supports bilingual interaction, where the spoken utterance and prompt language may differ.

\section{Perception Pipeline Implementation}\label{sec:server-perception-pipeline}

Figure~\ref{fig:architecture-perception-pipeline} gives the design view of the perception flow.
The server implements that flow in \texttt{PerceptionPipeline}.
The full run can include captioning, detection, tracking and memory association, Set-of-Mark rendering, scene graph generation, question generation, memory updates, and timing finalization.
Each stage records its name and timing metrics for dashboard inspection and the latency measurements in Chapter~\ref{chap:experiment}.

The pipeline has sequential and partially parallel execution modes.
In sequential mode, captioning runs first, then detection, followed by all post-detection stages.
In parallel mode, captioning and detection start concurrently on copied image objects.
The detector call is synchronous, so it is offloaded through \texttt{asyncio.to\_thread} and protected by a detector lock.
This prevents simultaneous access to one detector instance from multiple requests.
Later stages remain ordered because tracking depends on detections, SoM depends on tracked detections, and scene graph generation depends on detections and optionally the caption.

Detection is implemented behind a service abstraction whose registry can load YOLO, RT-DETR, RF-DETR, and OWLv2.
Regardless of backend, downstream stages receive normalized detections with class identifier, label, confidence, bounding box, and optional object identifier.
The thesis setup uses RF-DETR by default, with threshold and optional non-maximum suppression controls kept configurable because detector settings affect dialogue as well as vision: a false positive can become a spoken claim, while an overly strict threshold can hide an object visible to the user.

\section{Tracking and Memory Association}\label{sec:server-tracking-memory}

As discussed in Sections~\ref{sec:object-detection-tracking-reid} and~\ref{sec:architecture-scene-memory}, detection is frame-local while dialogue needs persistent references.
The tracking stage extracts a crop for each detection, computes a visual embedding, and matches current detections to existing tracks with the Hungarian algorithm.
The weighted cost is based mainly on visual similarity and partly on image-space geometry, with label equality as a hard constraint so an existing chair track cannot silently become a detected person.

Generic object embeddings use \texttt{nvidia/C-RADIOv4-SO400M} by default~\cite{nvidia_cradiov4_so400m_2026, ranzinger_c-radiov4_2026}.
For people, the implementation can use the Hugging Face port \url{https://huggingface.co/maennyn/personvit-reid-msmt17-vit-s}, based on the PersonViT project~\cite{hustvl_personvit_2026, hu2024personvitlargescaleselfsupervisedvision}.
This separates general object appearance matching from person-specific Re-ID when that mode is enabled.

Matched detections keep their object IDs; unmatched detections create new tracks, and dormant tracks are aged for later pruning.
Stable identifiers then carry the detections into SoM rendering and scene graph generation, allowing repeated observations to strengthen the same physical object instead of creating a new memory entry for every frame.

Memory update separates low-level tracking state from dialogue-facing object state.
Tracks keep visual features such as embedding, crop, box, confidence, hit count, and last-seen time; object records keep symbolic and embodied fields such as identifier, label, status, attributes, frame or scan identifier, bearing, robot distance, Pepper person identifier, and timestamps.

\section{Pepper Metadata Fusion}\label{sec:server-pepper-fusion}

Pepper metadata is fused with server detections after tracking, using the robot-side payload described in Section~\ref{sec:client-metadata}.
The client can send head pose, field of view, image size, and NAOqi people-perception records with a Pepper person identifier, yaw, pitch, distance, and social cues such as engagement zone, sitting, waving, gaze, smile, or expression.
Although noisy, these signals contain embodied information that an ordinary object detector does not provide.

The server projects Pepper-reported people into the image coordinate frame and compares their angular-distance evidence with detected person boxes.
When the match is plausible, the Pepper person identifier and social metadata are attached to the tracked object.
If Pepper reports a visible person but the detector misses the box, the server can create a lower-confidence synthetic person detection from the robot-reported direction and distance, preserving a socially relevant hypothesis that would otherwise disappear.

Robot-derived facts become object attributes in scene memory.
Sitting, waving, gaze, distance, and engagement zone can later be injected into the scene graph as self-relations and serialized into the chat context, connecting ordinary image perception with Pepper-specific social perception.

\section{Set-of-Mark and Scene Graph Generation}\label{sec:server-scene-graph-generation}

\begin{figure}[p]
\centering
\includegraphics[height=0.78\textheight]{pics/pipeline/04_som_scene_graph_nicer_nicer.pdf}
\caption{Set-of-Mark and scene graph stage. Tracked detections are rendered with persistent identifiers before the VLM scene graph backend is called. Rule-based, RelTR, and VLM relation sources are merged and filtered. Robot metadata can be added to person objects before memory is updated.}
\label{fig:server-som-scene-graph}
\end{figure}

Scene graph generation starts after detections have object identifiers.
Following the Set-of-Mark design in Section~\ref{sec:architecture-perception-pipeline}, the painter can overlay boxes, labels, masks, polygons, and object identifiers.
Runtime configuration controls line thickness, mask opacity, color lookup, and whether masks come from lightweight GrabCut or a SAM-based backend with fallback behavior.
The marked image lets the VLM refer to visible object instances by identifier instead of ambiguous natural-language description.

The implemented scene graph service combines optional rule-based, RelTR, and VLM backends, as shown in Figure~\ref{fig:server-som-scene-graph}.
Rules compute directional, proximity, and coarse color facts from boxes and crops.
RelTR proposes learned visual relations and maps predicted boxes back to current detections.
The VLM backend uses the raw or SoM image, prompt templates, current detections, optional captions, and the allowed vocabulary to produce subject--predicate--object triples whose identifiers refer to tracked detections.

Backend execution can be sequential or parallel.
Sequential execution runs rules, RelTR, and VLM in a fixed order.
Parallel execution can offload rules and RelTR to worker threads while the VLM backend runs asynchronously.
The outputs are still merged in deterministic backend order.
The merge is a union with deduplication, followed by enhancement with robot-derived attributes from scene memory.

The VLM backend is deliberately constrained.
It renders prompts from configured templates, calls the chosen provider, requests structured output when supported, and can ask the model to repair malformed JSON-like text without resending the image.
Parsed relations are then filtered against current detection identifiers; triples that refer to missing or hallucinated object IDs are removed because visually plausible text is not necessarily grounded in the tracked object set.

Structured output is validated through the same Pydantic schemas regardless of provider.
Cloud providers use native structured output when available, while local llama.cpp and Ollama-style servers are reached through OpenAI-compatible endpoints and can use Instructor with \texttt{Mode.JSON}~\cite{instructor_docs_2026}.
In practice, this mode was more reliable than \texttt{Mode.TOOLS} for smaller local models, such as GGUF variants of Qwen3.5-0.8B~\cite{unsloth_qwen35_08b_gguf_2026}; if it fails, the server falls back to JSON text and schema validation.

\section{Scene Memory and State}\label{sec:server-scene-memory}

Scene memory, introduced architecturally in Section~\ref{sec:architecture-scene-memory}, is implemented as the server's in-memory world model.
It stores tracked objects, relationships, captions, object crops, and Pepper person bindings.
In worker mode it lives in the worker process, which owns the active perception pipeline; API services access it through the runtime adapter or memory proxy so public route behavior remains unchanged.

Object records combine visual and embodied fields: identifier, label, status, source, attributes, bounding box, timestamps, hit count, frame or scan identifier, bearing, Pepper person identifier, robot distance, and engagement zone.
Relation records keep subject identifier, predicate, object identifier, first-seen time, last-seen time, and count, while caption records keep text with provider, model, source, frame or scan identifier, and timestamps.

Scene graph memory update reads numeric graph edges.
An edge whose subject and object are the same instance becomes a unary attribute; otherwise it creates or refreshes a binary relationship.
Repeated relationships increment their count and update their last-seen timestamp, which is why scene graph backends must preserve correct object identifiers rather than relying on labels alone.

Memory is bounded by age and capacity.
Objects, relations, captions, tracks, and Pepper bindings are pruned when they become stale or exceed configured limits.
This prevents the robot from treating old observations as current facts.
For example, if a cup was detected several minutes ago and has not been seen again, it should not dominate the next answer as if it were still certainly present.

The memory API exposes this state as a first-class resource.
Clients can request the full scene state, compact summaries, crops, object and relation lists, reset operations, and manual create, update, or delete operations.
The summary used by the dashboard and robot tablet contains labels, counts, graph relations, an SVG graph, and pregenerated question-answer pairs.

\section{Dialogue, Captions, and Question Generation}\label{sec:server-dialogue-services}

The server uses provider adapters for language and vision-language models.
The same orchestration code can call OpenAI, Gemini, local OpenAI-compatible servers, and local Hugging Face providers where configured.
The abstraction keeps stable interfaces for chat, VLM, captioning, structured generation, and translation without pretending that structured output and multimodal behavior are identical across providers.

The chat service converts scene memory into prompt context as defined in Section~\ref{sec:architecture-scene-memory}.
For general chat, it serializes remembered objects, attributes, relations, and recent captions, ordering objects by a salience heuristic that favors people, social facts, distance, recency, and hit count.
The language model is then asked to answer from this context rather than from parametric knowledge alone.

Object-focused chat builds a narrower context.
If the robot client sends an object label recognized by QiChat, the server matches current memory objects by normalized label and includes the relevant object records and neighboring relations.
If the object has few structured facts but a stored crop is available, the service can request a caption of the crop as a fallback.
This improves object-focused answers when detection succeeded but scene graph generation produced little information about the object.

The conversation service stores recent message history.
It preserves the original user-facing text and the model-facing text separately.
This supports bilingual operation, because a Czech utterance may be displayed and logged as originally spoken while an English or normalized form is used for prompt history.
The same distinction can be kept for assistant responses.

Question generation is a latency optimization.
After scene graph generation, the server can generate graph-grounded question-answer pairs and ingest them into a bounded QA pool when memory is updated.
The robot can expose these questions through the tablet or QiChat dynamic concepts; cached questions are answered immediately, while other questions fall back to ordinary chat.

The vision-chat route remains separate from memory-grounded chat.
It sends an image and question directly to a VLM for dense visual reasoning that may not be represented in the current graph, but it is not the mechanism for maintaining persistent scene memory.

\section{Dashboard, Configuration, and Worker Control}\label{sec:server-dashboard}

% \centering

The dashboard is the developer-facing view of the same runtime state used by Pepper.
It receives WebSocket events for detections, captions, memory updates, and chat messages, and exposes the current image, caption, chat log, memory graph, object lists, relation lists, and generated question-answer pairs.
%Figure~\ref{fig:dashboard} shows the main dashboard page, which is used to inspect the current robot observation and the scene memory built from it.

Manual controls allow a developer to send chat messages, inspect model outputs, reset memory, and insert or edit objects and relations.
During testing, a wrong robot answer can originate in speech recognition, image capture, detector output, tracking, scene graph generation, prompt construction, translation, or the LLM response; the dashboard makes these intermediate states visible.

\centering
\includegraphics[width=1\linewidth]{pics/example_dashboard_translation_sgg_settings_vertical.png}
\caption{Dashboard configuration views for translation and scene graph generation. The server exposes runtime settings for label, predicate, and attribute translation, as well as scene graph backend and Set-of-Mark controls.}\label{fig:dashboard-translation-sgg-settings}
\end{figure}

Figure~\ref{fig:dashboard-translation-sgg-settings} shows translation and scene graph configuration views.
Translation settings map normalized labels, predicates, and attributes to robot-facing language output.
Automatic translation uses googletrans~\cite{googletrans_pypi_2026}.
Scene graph settings expose backend and prompting controls, including rule-based relations, RelTR, VLM generation, Set-of-Mark rendering, labels, boxes, masks, polygons, and related thresholds.

Configuration changes are divided into hot updates and hard reloads.
Thresholds, prompt paths, selected runtime flags, translation mappings, and some provider parameters can be pushed into a running runtime; changes that rebuild model objects require a hard reload.
In worker mode, that reload restarts only the worker process, keeping the public API separate from model teardown and GPU memory release.

The worker manager tracks state, process identifier, configuration version, inflight requests, health checks, idle shutdown, restart counts, crash counts, and last errors.
This separation lets the public server keep serving status and fallback responses while a local model process slows down, fails, or releases GPU memory.

The server implementation is therefore an integration layer under embodied constraints.
It does not contribute a new detector or language model; it connects configurable perception, tracking, robot metadata fusion, scene graph generation, memory, and language services into a runtime that Pepper can call.
Chapter~\ref{chap:robot_side_rewrite} describes the client side of that boundary.

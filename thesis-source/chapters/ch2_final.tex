\chapter{Background and Related Work}\label{chap:background}

Chapter~\ref{chap:intro} introduced the thesis problem: enabling Pepper to answer questions about its surroundings using visual perception, persistent scene memory, and language generation. This chapter reviews the background needed for that goal: HRI and Pepper dialogue, visual perception and object persistence, scene-graph grounding, Set-of-Mark prompting, and language-model context construction.

\section{Human-Robot Interaction and Pepper Dialogue}\label{sec:hri-social-robots}

Human-robot interaction (HRI) studies how humans and robots interact in shared tasks. Goodrich and Schultz frame HRI as work across robotics, human factors, psychology, design, linguistics, and computer science~\cite[203--216]{goodrich_human-robot_2007}. In this setting, Pepper is not just a camera or a text generator; it is an embodied system that speaks, displays information, occupies the scene, and sometimes fails in front of a user.

Sheridan distinguishes social interaction from supervisory control, teleoperation, and automated vehicles~\cite[525--526]{Sheridan2016HRI}. This thesis belongs to the social-interaction setting. Pepper is not used as a manipulator or navigation platform, but as a communication partner that should answer questions about its perceived environment.

Social robots are not defined by their shape. Henschel et al.\ note that the term [social robot] does not have a single universal definition, but that common elements include embodiment, autonomy, and behavior that people interpret as social~\cite[11--12]{henschel_what_2021}. For Pepper, this means that even a simple scripted action can be interpreted as part of an interaction: speech, gaze, waiting, and physical presence are perceived together rather than as isolated software outputs.

Embodiment raises expectations that a purely text-based assistant does not face. A user may assume that a robot standing in the same room can refer to nearby objects, distinguish people, or remember a previously mentioned item. Henschel et al.\ report that Pepper users expected reciprocal conversation and noticed the limits of single-turn interaction~\cite[12]{henschel_what_2021}. LLM-supported HRI has a related risk: fluent language can suggest broader situational competence than the system actually has~\cite{kim_understanding_2024,aturhurra_leveraging_2024}.

Embodiment can also improve how users experience a conversational system. Gava et al.\ compared an embodied robot setup with an application using the same conversational framework and report more positive ratings for the robot condition in perceived reliability, awareness of system behavior, speech quality, and ease of mistake correction~\cite{gava2024physical}. The result is preliminary, but it supports a practical design assumption used here: the robot body is part of the interaction, not only a container for a chatbot. It makes failures of perception, latency, and memory visible, while also making successful grounded answers more useful.

Pepper provides interaction services through NAOqi, including speech, tablet output, camera access, people perception, behavior control, and dialogue modules~\cite{softbank_python_sdk_2026}. These services make Pepper practical for situated dialogue because one application can listen, speak, move, display information, and capture images. However, the native stack does not by itself provide open-ended grounded answers about changing visual memory~\cite{softbank_alspeechrecognition_2026}.

Pepper dialogue is commonly built with ALDialog and QiChat-style topics. A topic defines patterns that match recognized utterances and proposals that the robot can say. This rule-based approach is reliable for bounded commands, confirmations, and menu-like interaction, but it does not infer arbitrary facts about the world. Its strength is that recognized language can be routed to deterministic actions, including Python-side methods that make the robot speak, move, show tablet content, or call external services, with low overhead~\cite{noauthor_qichat_nodate}.

Dynamic concepts make this rule-based layer more flexible. Instead of hard-coding every possible object name or relation into the grammar, the application can update a concept at runtime with scene-dependent words~\cite{noauthor_qichat_nodate}. A scene-aware dialogue system can therefore use a relatively static QiChat topic for intent recognition while external perception and memory supply the current object labels, attributes, relations, or pregenerated questions.

\section{Object Detection and Object Persistence}\label{sec:object-detection-tracking-reid}

Object detection provides the first layer of visual evidence. It identifies object instances in an image and localizes them, most commonly by bounding boxes. A detector maps an image \(I\) to a finite set
\[
\mathcal{D}(I)=\{(b_i,\ell_i,s_i)\}_{i=1}^{N},
\]
where \(b_i\) is a bounding box, \(\ell_i\) is a class label, and \(s_i\) is a confidence score~\cite[Section 50.4.1]{foundationsCVbook}.

Modern object detection was strongly shaped by convolutional neural networks, which exploit spatial structure in images through learned local filters and hierarchical visual features~\cite[439]{lecun_deep_2015}. One influential practical family is YOLO, short for \emph{You Only Look Once}. YOLO-style detectors process the image in a single forward pass and predict bounding boxes, confidence scores, and class probabilities from dense image features~\cite{redmon_you_2016}. This efficiency makes them attractive when latency matters, and modern YOLO implementations preserve the same general idea while adding improved backbones, multi-scale feature fusion, detection heads, confidence filtering, and usually non-maximum suppression~\cite{sapkota_ultralytics_2026}.

DETR-style detectors take a different view. Instead of treating detection primarily as dense prediction over spatial feature locations, DETR formulates it as set prediction~\cite{carion_end--end_2020}. Learned object queries predict a set of hypotheses, and training matches predictions to ground-truth objects with bipartite matching. Thus, YOLO emphasizes efficient single-pass dense prediction, while DETR emphasizes direct set prediction and reduces dependence on heuristic duplicate removal. This family is relevant because the implemented system uses RF-DETR and RT-DETR as two possible detector backends; RF-DETR follows the real-time detection-transformer direction and is designed around accuracy-latency tradeoffs for practical detection~\cite{robinson_rf-detr_2026}.

The afore\-mention\-ed object detectors all belong to closed-vocabulary detectors. Closed-vo\-ca\-bul\-ary detectors predict labels from a fixed ontology. COCO is a common example, containing everyday object categories widely used in detection benchmarks and pretrained detectors~\cite{lin2015microsoftcococommonobjects}. This approach is practical and stable, but limited by the labels available during training. In an office, classroom, or computer laboratory, users may refer to objects that are too specific, rare, or task-dependent for the detector's fixed label set.

Open-vocabulary detection addresses this limitation. Models such as OWL-ViT and OWLv2 compare visual regions with text queries, allowing labels to be supplied at inference time~\cite{minderer_simple_2022,minderer_scaling_2024}. This flexibility is attractive for dialogue about environment-specific objects, but it also makes detections sensitive to prompt wording, label granularity, and score calibration. Open-vocabulary outputs must therefore be treated as evidence rather than as guaranteed facts.

Detection is inherently frame-local. It does not decide whether a chair seen now is the same chair seen earlier. In continuous video streams, this problem is usually handled by multi-object tracking. Tracking-by-detection methods such as SORT, Deep SORT, and ByteTrack associate detections across adjacent frames using motion, geometry, confidence, and sometimes appearance information~\cite{bewley_simple_2016,wojke_simple_2017,zhang_bytetrack_2022}. These methods work best when consecutive frames are temporally and spatially close.

Pepper's observations in the implemented system are often discontinuous. The robot may capture one image, speak, move its head, capture another image from a different viewpoint, and later answer a follow-up question. Between such observations, an object may shift strongly in image coordinates or disappear from the field of view. Pure frame-to-frame tracking is therefore not sufficient for persistent scene memory.

This motivates re-identification (Re-ID), which asks whether two observations correspond to the same physical instance across different times, views, or contexts~\cite[22--23]{zheng_object_2024}. Here, the relevant mechanism is appearance-based matching of object crops. A crop from the current image can be compared with crops stored in a gallery; if the visual evidence is sufficiently similar and the labels are compatible, the system may treat the detections as the same object instance.

Re-ID is often described as a query-gallery problem. The current crop is the query, and previously stored crops form the gallery. A feature extractor maps crops into an embedding space where instance-specific cues are preserved, while remaining robust to changes in lighting, scale, or viewpoint~\cite[22]{zheng_object_2024}. The task is therefore different from category recognition: it is not enough to decide that two crops are both chairs; the system must decide whether they depict the same chair.

Pepper also provides native people-perception modules through the NAOqi API. ALPeoplePerception can expose visible people and their associated IDs, which can be used to fetch related signals such as estimated age, distance from the robot, or gaze direction. ALFaceDetection can also detect and optionally recognize faces after learning.\footnote{See the Aldebaran documentation for ALPeoplePerception and ALFaceDetection: \url{http://doc.aldebaran.com/2-4/naoqi/peopleperception/alpeopleperception.html} and \url{http://doc.aldebaran.com/2-4/naoqi/peopleperception/alfacedetection.html}.} These modules are useful for human-centered interaction, but they are not a general object-persistence solution: they apply primarily to people and depend on visibility, pose, distance, and prior enrollment. In the thesis system, they are best understood as auxiliary robot metadata that can support visual memory.


\section{Grounding and Scene Graph Generation}\label{sec:grounding-sgg}


In robotics, grounding means linking linguistic expressions to entities, attributes, and relations in the perceived world. Lemaignan et al.\ describe situated grounding as a connection between perception, symbolic knowledge representation, and dialogue processing~\cite[181--182]{lemaignan_grounding_2012}. Grounding is not achieved by adding an image to a prompt alone; the system needs a representation in which a phrase such as \enquote{the object next to the laptop} can be connected to perceived objects and relations.

A list of detections is insufficient for many grounded questions. It may contain object labels and bounding boxes, but not the relational structure needed to answer whether a cup is on a table, a person is wearing glasses, or a keyboard lies to the left of a monitor.

Captions can summarize a scene in natural language and have been used as grounding evidence in conversational robot systems~\cite{grassi_grounding_2024}. However, captions do not reliably expose object identities and relations in a reusable structure.

Scene graphs provide a more suitable representation for this missing structure. Johnson et al.\ define a scene graph as a data structure that encodes object instances, object attributes, and relationships between objects~\cite[3668--3669]{johnson_image_2015}. A simple formulation is
\[
\mathcal{G}=(\mathcal{O},\mathcal{E}),
\]
where \(\mathcal{O}\) is a set of object instances and \(\mathcal{E}\subseteq \mathcal{O}\times\mathcal{R}\times\mathcal{O}\) is a set of directed relationship edges. A binary relation can be written as a subject-predicate-object triplet \((s,p,o)\), for example \((\text{cup},\text{on},\text{table})\). Attributes can be stored as node properties or unary labels. Zhu et al.\ summarize scene graphs in the same practical way: as structured representations of objects, attributes, and relationships~\cite[3]{zhu_scene_2022}.

Scene Graph Generation (SGG) is the task of producing this structure from visual input. Classical SGG is often organized in two stages: first detect objects, then predict predicates for candidate object pairs. Learned methods rely on object labels, visual features, pair geometry, context, and dataset priors to predict relation triplets correctly~\cite[5]{zhu_scene_2022}. The difficulty lies especially in relationship prediction. Predicate distributions are long-tailed, relation labels can be semantically ambiguous, and object-detection errors propagate into the graph. A missed object removes all relations involving that object; a wrong label or unstable identity can make a correct relation unusable in dialogue.


RelTR is a representative of the one-stage alternative. It builds on the set-prediction idea from DETR, but predicts a sparse set of subject-predicate-object triplets directly instead of enumerating all possible object pairs and classifying predicates for each pair. RelTR uses entity representations, subject and object branches, and learned triplet queries to decode relation candidates. The final output includes subject and object classes and boxes together with a predicate label~\cite{cong_reltr_2023}.


A newer option is Vision-Language model (VLM) based SGG. Instead of treating relation prediction only as fixed predicate classification over detected object pairs, recent work formulates SGG as promptable image-to-text or image-to-sequence generation. This is attractive when the target vocabulary is open, domain-specific, or not well covered by standard SGG datasets.

IndVisSGG is a relevant example. It uses VLMs for scene graph generation in industrial spatial-intelligence settings, with GPT-4V-based multi-agent processing over video frames. Its inputs include visual information, predefined object categories, predicate dictionaries, and positive and negative examples. The prompt specifies scene-graph information, triplet extraction criteria, and output-format requirements. The process extracts spatial-temporal triplets, checks omissions, redundant entities, and predicate-rule violations with multiple expert agents, and summarizes spatial and interactive relations into the final graph. Figure~\ref{fig:indvissgg-background} illustrates this pipeline~\cite{wang_indvissgg_2025}.

IndVisSGG is close to the methodological direction of this thesis even though the domain is different: it combines a constrained object and predicate vocabulary, prompt criteria, visual input, and correction around generated triplets. PGSG, or Pixels to Scene Graph Generation with Generative VLMs, provides another example. Li et al.\ formulate open-vocabulary SGG as generation of a textual scene-graph sequence from an image, using relation-aware tokens to represent subject-predicate-object structure and a relation-construction module to convert the generated sequence into instance-level triplets~\cite{li_pixels_2024}.

PGSG also includes grounding and category conversion modules that recover bounding boxes and map generated words to benchmark object and predicate categories~\cite{li_pixels_2024}. Its methodological relevance here is twofold: VLMs can act as flexible relation generators for a domain-specific vocabulary, but their outputs still require grounding, normalization, filtering, and schema control before they can be stored in scene memory.

The main limitation is output control. A generative model may invent unsupported relations, use inconsistent predicate names, ignore object identifiers, or produce malformed structure. If a VLM is asked to produce relations between detected objects, it must also refer to the same object instances as the detector and memory system. This need for reference alignment motivates Set-of-Mark prompting.

\section{Set-of-Mark Prompting}\label{sec:set-of-mark}

Set-of-Mark prompting marks visible image regions with explicit identifiers before the image is passed to a VLM. Instead of asking the model to infer which of several similar chairs is meant by \enquote{the chair}, the prompt can ask about \enquote{object 4}. Yang et al.\ describe this as a visual prompting method in which the original image is transformed into a marked image before querying the VLM. Their central observation is that marks such as numbers and masks make image regions both visually highlighted and linguistically referable, which in turn produces more factually correct results~\cite{yang_set-of-mark_2023}. The technique is illustrated in Figure~\ref{fig:som-prompting-background}.

\begin{figure}[!htbp]
\centering
\includegraphics[width=1\linewidth]{pics/som_prompting_original_pic.png}
\caption{Illustration of standard VLM prompting compared with Set-of-Mark prompting. Visual marks make image regions explicitly referable, reducing ambiguity when the model must answer about a specific object. Reproduced from Yang et al.~\cite{yang_set-of-mark_2023}.}\label{fig:som-prompting-background}
\end{figure}

The method first partitions the image into meaningful regions, for example with segmentation or detection models, and then overlays each region with a unique number, letter, mask, box, or combination of marks. The mark must be easy for the VLM to perceive and easy for the language model to mention in text. Numeric or alphabetic labels are useful because the model can answer with \enquote{region 3} or \enquote{object B} instead of uncertain coordinates. In low-resolution or cluttered images, however, marks can cover visual evidence or add noise that may degrade performance.

For scene-aware dialogue, the main value of Set-of-Mark prompting is alignment. Detector IDs, graph nodes, VLM references, tablet visualization, and later spoken answers can be tied to the same marked object. This is particularly important in scenes with repeated objects, such as multiple chairs, monitors, books, or people.

\section{Language Models, Vision-Language Models, and Scene Context}\label{sec:llms-vlms-context}

Large language models are useful in dialogue because they can generate fluent responses conditioned on an instruction and context. Instruction tuning and preference-based alignment make such models more suitable for interactive use than raw pretrained language models~\cite{ouyang2022traininglanguagemodelsfollow}. For grounded robot dialogue, fluency must be constrained by evidence: the model can answer correctly about the scene only if the relevant scene state is present in its context or accessible through retrieval.

Vision-language models extend language generation or visual representation learning with image input~\cite[2--3]{zhou_large_2026}. Some models use shared image-text embedding spaces, which support retrieval and open-vocabulary perception. Others connect visual encoders to language models and generate text conditioned on both the prompt and the image. This property makes VLMs attractive for captioning and draft scene-graph generation, but it also creates risk: a VLM may hallucinate objects, ignore a required schema, or use relations outside the intended vocabulary.

In a social robot, such mistakes are not only technical. The user may see the same room as the robot, so an unsupported answer can immediately break trust or fail to satisfy the user's information need. For this reason, grounded systems should treat LLM and VLM outputs as hypotheses to be constrained, checked, or stored with provenance rather than as direct truth.

One way to lower hallucination risk is to provide relevant evidence. Retrieval-Augmented Generation (RAG) combines a generator with external evidence retrieval~\cite{lewis_retrieval-augmented_2020}. In ordinary text settings, the evidence is often a set of document chunks retrieved by semantic similarity to the query.

For scene-aware dialogue, the evidence is better viewed as scene memory: objects are nodes, attributes are node properties, and relationships are edges. A question such as \enquote{what is next to the monitor?} should retrieve the monitor and its graph neighborhood, not just the most semantically similar text fragment.

Cache-Augmented Generation (CAG) uses a different assumption: if the relevant knowledge is bounded and fits into the model context or cache, it can be loaded once and reused without online retrieval~\cite{Chan_2025}. This idea fits small current-scene memories, where the full scene summary may fit into a prompt. Its limitation is shared by all context-construction methods: irrelevant or stale evidence can distract the model, while missing evidence prevents grounded answers.

The practical consequence is that captions, scene graphs, cached questions, and object-focused summaries are different routes from visual memory to language-model input. The implementation details belong to later chapters; the common principle is that the dialogue model should answer from maintained scene state, not from pretrained world knowledge alone.

\section{Pepper Robot Specification}\label{sec:pepper-specification}

Pepper is a humanoid social robot designed by Aldebaran Robotics in 2014 and manufactured until 2020. It provides speech output, microphones, cameras, a chest tablet, expressive head and arm motion, and a mobile base. In this thesis, Pepper is treated primarily as an embodied communication system rather than as a manipulation system. Its role is to support situated dialogue about the visible environment, not to physically modify that environment.

Pepper's technical specification is relevant because it defines the computational and software constraints under which the system must operate. Public specifications list an Intel Atom E3845 CPU, 4 GB RAM, and 32 GB eMMC flash memory in the main CPU module, together with RGB cameras, microphones, speakers, sonars, lasers, bumpers, and the chest tablet.\footnote{See the Pepper technical specifications: \url{https://aldebaran.com/support/kb/pepper/general/pepper-technical-specifications/}.} These resources are appropriate for Pepper's native interaction, sensing, motion, and dialogue modules, but they provide limited headroom for computationally demanding neural inference.

In addition, Pepper's NAOqi software environment relies on legacy Python 2 interfaces, while contemporary ob\-ject-de\-tec\-tion, vi\-sion-lan\-guage, lan\-guage-mod\-el, and scene-graph-gen\-er\-a\-tion frameworks are developed primarily for modern Python 3 ecosystems and often assume hardware acceleration. For this reason, these models are not deployed directly on the robot. Instead, Pepper is used as the embodied interaction client, while the more demanding perception and lan\-guage-pro\-cess\-ing components are executed on an external machine. This constraint motivates the cli\-ent-serv\-er architecture described later in the thesis.

This chapter therefore establishes the concepts used by the rest of the thesis. Pepper dialogue supplies the interaction layer, hardware constraints motivate external computation, object detection and persistence provide visual entities, scene graphs organize those entities for grounding, Set-of-Mark prompting aligns visual references, and language models turn selected scene state into spoken answers.

\chapter{Server-Side Implementation}\label{chap:server_side_rewrite}

The server is the most important part of the system. Its role is to receive images, parse robot metadata, run the perception pipeline, and generate answers based on the current scene memory while also exposing controls and state of the app in the dashboard. Chapter~\ref{chap:system_architecture_rewrite} introduced this component at the system level. Present chapter describes the server in greater detail, the following Chapter~\ref{chap:robot_side_rewrite} will describe the robot side, the client, which calls the server's endpoints.

\section{Runtime Structure and Public Boundary}\label{sec:server-runtime-structure}

The public process is a FastAPI Python application. 
It exposes the REST API under \texttt{/api/v1}, serves the dashboard under \texttt{/dashboard}, mounts static dashboard assets, and opens a WebSocket endpoint for live dashboard events. 
This boundary keeps the Pepper-side NAOqi program separated from the inference stack. Pepper only sees the stable HTTP endpoints useable for detection, captioning, memory summaries, and chat; the server can then change detector backends, model providers, prompts, and runtime mode without changing the robot application in any way.

Figure~\ref{fig:server-runtime-structure} shows the main server components. 
The route layer is organized around system capabilities. Perception routes are \texttt{api/v1/detect}, \texttt{api/v1/detect/panorama}, and \texttt{api/v1/caption}. 
Dialogue routes are \texttt{api/v1/chat} and \texttt{api/v1/vision\_chat}. 
State routes provide memory CRUD operations, configuration update, and worker status management.

\centering
\includegraphics[width=\linewidth]{pics/dashboard_screenshot.png}

The dashboard is served at \texttt{/dashboard} and provides way to control the runtime, and view all the processed inputs and memory state which are broadcasted to it using websocket. 
The user can also interact with all API endpoints through it directly, i. e. changing system prompts, switching between parallel and sequential pipeline execution, insert synthetic objects into memory or upload images for processing and chat with the RAG enhanced LLM. Dashboard screenshot is shown in Figure~\ref{fig:dashboard}.

%The same route layer is used by the Pepper client and by the dashboard, although the dashboard also receives live updates through WebSocket broadcasts.

The central runtime object is \texttt{AppState}. It stores the active configuration, the configuration version, the optional in-process pipeline, the optional worker manager, the chat service, the caption service, the conversation service, the generated question-answer pool, and the last published state. This is the dependency root of the server. The routes do not construct detector or language-model objects directly; they resolve services from this shared runtime state.

The server supports two execution modes. In in-process mode, the public FastAPI application owns the perception pipeline directly, e. g. it runs it in the same process. In worker mode, the public process starts a second internal FastAPI application and forwards heavy inference requests to it. The prefered configuration for deployment is the worker mode. This setup is useful because in in-process mode the object detectors, VLMs, caption models, and embedding models can allocate substantial GPU memory which is not freed and made able to be reallocated until the end of process. The worker processes thus utilizes the needed GPU resources for the minimum time required thanks to managmenet of another process which can be killed and restarted when needed. The public server process remains a lighter HTTP and orchestration layer, while the worker owns the heavy model objects and the scene memory used by the pipeline.

The code hides this deployment choice behind a runtime adapter. The in-process adapter opens the uploaded image and calls the local pipeline. The worker adapter serializes the same request and sends it to the internal worker API in an RPC manner. The higher-level services therefore use the same contracts in both modes. This is important for the implementation, as it creates a single source of truth for inference.

\section{Requests and Pipeline Execution}\label{sec:server-perception-pipeline}

The main perception request is a multipart image upload with optional JSON robot metadata. Metadata contains fields such as head yaw and pitch, camera field of view, frame and scan identifiers, image size, battery state, and Pepper people-perception outputs. The server parses this into typed Pydantic schemas before inference. %If field-of-view values arrive in degrees, the boundary parser normalizes them to radians, so the rest of the pipeline can use one convention.

\begin{figure}[p]
\centering
\includegraphics[height=0.9\textheight]{pics/pipeline_less_detailed.pdf}
\caption{Perception pipeline overview. The pipeline consists of captioning for fast description of the scene and object detection for futher scene modeling, ReID, scene graph generation, question-answer (QA) pairs pregeneration and memory updates. Captioning and detection can run sequentially or in parallel.}\label{fig:server-perception-pipeline}
\end{figure}

Figure~\ref{fig:server-perception-pipeline} summarizes the pipeline. In the full configuration, the server can run captioning, object detection, tracking and memory association, Set-of-Mark rendering, scene graph generation, question generation, caption memory update, and scene graph memory update. Each stage records and logs timing metrics. Not all stages of the pipeline are needed, a request can still return useful detections and memory updates even if captioning or relation generation fails. Every pipeline stage is also configurable in the dashboard in the corresponding tabs, as well as the pipeline constitution can be changed --- some stages can be dropped.

The pipeline has a sequential mode and a partially parallel mode. In sequential mode, captioning runs first, then detection, then the post-detection stages. In parallel mode, captioning and detection start at the same time on separate image copies. Detection can be offloaded to a thread and guarded by a detector lock, while the caption request can wait on a remote or local provider. After both branches are ready, the pipeline joins the outputs and continues with tracking, SoM rendering, scene graph generation, memory updates, and question generation. This parallelism is optional because the best choice depends on hardware, provider latency, and model memory pressure. Further parallelism of the pipeline is not possible as all the subsequent stages depend on the output of these two stages and on the output of the preceeding stage (e.g. scene graph generation can use captions in the user or system prompt if needed to provide hints for the VLM). 

There is a second parallelism switch inside scene graph generation. The scene graph service can run rules, RelTR \cite{cong_reltr_2023}, and the VLM backend sequentially, or it can run the rule and RelTR backends in worker threads while the VLM backend runs asynchronously. The generated graphs are then merged with a union and deduplication strategy. %The current configuration keeps this parallelism disabled, which favors simpler timing and easier debugging during development.

\section{Object Detection Backends}\label{sec:server-detection-backends}

Object detection is implemented behind a common detector interface. The current registry can load YOLO, RT-DETR, RF-DETR, and OWLv2 backends. Regardless of the model family, each backend returns the same internal schema; class identifier, label, confidence, bounding box, and optional object identifier. This normalization is central to the architecture as tracking, Set-of-Mark rendering, scene graph generation and other stages should be agnostic of the used detection backend.

The DETR family is the conceptual base for RT-DETR and RF-DETR. Traditional detectors often generate many candidate boxes and then remove duplicates with post-processing such as non-maximum suppression. As mentioned in section \ref{sec:object-detection-tracking-reid}, DETR instead treats detection as direct set prediction.

RT-DETR adapts this idea for real-time use. Its authors argue that DETR-style detectors can be made competitive with YOLO-style real-time detectors by improving the encoder and query selection. RT-DETR uses an efficient hybrid encoder to process multi-scale features and an uncertainty-minimal query selection mechanism to initialize higher-quality decoder queries. It also allows speed adjustment by changing the number of decoder layers without retraining~\cite{zhao_detrs_2024}. In this server, RT-DETR is useful as a ready-to-use backend when a deployment wants a real-time transformer detector with an Ultralytics loading path.

RF-DETR is the default detector in the current configuration. It is also a detection transformer, but it is presented as a lightweight specialist detector that uses weight-sharing neural architecture search to explore accuracy-latency tradeoffs for target datasets~\cite{robinson_rf-detr_2026}. In implementation, the server loads the Roboflow RF-DETR large model through the \texttt{rfdetr} package,\footnote{\url{https://pypi.org/project/rfdetr/}} optimizes it for inference, and maps predictions to COCO class names. This makes it practical for the thesis system; it provides strong off-the-shelf closed-vocabulary object detection without requiring custom detector training before the rest of the scene-aware dialogue pipeline can be tested.

OWLv2 serves a different purpose. It is an open-vocabulary detector, so the category list can be supplied as text rather than fixed entirely by the detector's supervised training label set. OWL-ViT first showed a simple vision-transformer approach for open-vocabulary detection with text-conditioned categories~\cite{minderer_simple_2022}. OWLv2 scales the same direction with self-training, using pseudo-box annotations on image-text data to improve open-world localization~\cite{minderer_scaling_2024}. In the server code, OWLv2 first receives an ontology list, caches the encoded text inputs so it can be reused and not be recomputed on each call. Upon call it runs the image through the Hugging Face model and processor, and returns grounded boxes with text labels. This is useful when the task needs labels that are not covered well by COCO, although it also requires careful threshold and ontology selection.

THIS IS BIT BLABLABLA: The detector service includes confidence thresholds and optional post-filtering with non-maximum suppression. Even when a model family is designed to reduce duplicate predictions, the server keeps these controls available because the downstream cost of a false object is high. If the detector invents a laptop, the memory and the dialogue prompt can turn that into a spoken claim. If the threshold is too strict, the robot may ignore an object that the user can clearly see. The detection configuration therefore trades recall against dialogue honesty, not only computer vision metrics.

\section{Tracking, Re-identification, and Pepper Metadata}\label{sec:server-pepper-fusion}

Detection alone is per-frame perception. The dialogue system needs persistent object identities, because the user may ask follow-up questions after a scan or after the object has temporarily left the current frame. The server therefore updates scene memory after detection. It crops each detection, extracts visual embeddings, and matches detections to existing tracks using the Hungarian algorithm. The configured association cost combines visual distance and image-space geometry derived from the robot metadata, with label equality as a hard constraint. %A previous chair track should not silently become a detected person.

The configured feature extractor is NVIDIA C-RADIOv4-SO400M, used through the local embedding code for object re-identification~\cite{ranzinger2026cradiov4techreport,nvidia_cradiov4_so400m_2026}. C-RADIO provides general visual representations that are useful when the system must compare cropped objects across discontinuous observations. The code also contains support for a PersonViT-based human re-identification model, with a ported MSMT17 ViT-S checkpoint available on Hugging Face.\footnote{Original code: \url{https://github.com/hustvl/personvit} Ported model: \url{https://huggingface.co/maennyn/personvit-reid-msmt17-vit-s}} The use of this or other models can be configured in the dashboard under the memory tab.

Pepper metadata is fused with visual detections after tracking. The client can send Pepper people-perception records, including person identifiers, yaw, pitch, distance, and social signals acquired from NAOqi APIs. The server projects the robot reported person direction into the image coordinate frame and compares it with detected person boxes (A very similar idea used for making Pepper grasp objects while using depth sensor can be found in \cite[4]{wang_target_2024}.). It can then attach Pepper person identifiers, distances, engagement zones, waving, sitting, looking-at-robot, gaze, smile, expression, and demographic signals to the tracked object state when the confidence checks pass.

The fusion code also handles a difficult case; Pepper may report a person while the visual detector misses the box. In that situation, the server can create a synthetic person detection from the robot-reported angle and distance. This is less visually reliable than a normal detector box, so it should be understood as a pragmatic social-perception cue rather than as ordinary image evidence stemming from the idea that people and people-like objects are the most important for social interactions with the robot. It prevents the system from losing an interaction-relevant object only because the camera detector failed on that frame.

\section{Set-of-Mark and Scene Graph Generation}\label{sec:server-scene-graph-generation}

Scene graph generation starts after detections have stable object identifiers, as we can see in Figure \ref{fig:server-som-scene-graph}. The SoM painter overlays boxes, labels, and optional masks or polygons onto the image. In the current configuration, boxes, labels, and polygon outlines are shown, while masks are disabled and GrabCut is the default mask backend. The purpose of SoM is grounding. A VLM can refer to \enquote{object 4} instead of ambiguously describing \enquote{the chair on the left}. Set-of-Mark prompting was introduced as a way to improve visual grounding in VLMs by making image regions explicitly referable~\cite{yang_set-of-mark_2023}.

The scene graph service combines three relation sources. The rule backend computes transparent geometric relations from boxes, such as \texttt{left\_of}, \texttt{right\_of}, \texttt{above}, \texttt{below}, \texttt{near}, \texttt{next\_to}, \texttt{far\_from}, and \texttt{in\_front\_of}. The RelTR backend proposes learned visual relations. The VLM backend uses the raw or SoM image, the current detections, the caption if available, and an allowed predicate list (all of these apart from the image can be added or removed from the prompt in the dashboard). The resulting graphs are added together and deduplicated, then robot-derived attributes from scene memory can be inserted as self-relations.

RelTR is included because it predicts scene graph triplets directly with a transformer relation model~\cite{cong_reltr_2023}. Instead of enumerating every possible object pair and classifying all pairs independently, RelTR uses learned queries to decode sparse subject-predicate-object relations. For this server, that makes it a useful learned relation proposal source. It is not treated as the only authority; its outputs are thresholded, matched to current detections, and merged with rules and VLM relations before memory is updated. An example of RelTR and VLM generated scene graph can be seen in Figure~\ref{fig:sgg-example}.

The VLM relation backend is deliberately constrained. It asks for structured output matching the scene graph schema, then parses the result. If the provider supports native structured output, the server requests it. If it does not, the code can use Instructor\footnote{\url{https://pypi.org/project/instructor/}} where available or fall back to prompting and JSON parsing. If parsing fails, the backend attempts a repair call to the VLM without providing the image again to save tokens and then filters relations against the current object identifiers. This is necessary because strict JSON can make model behavior brittle, while unconstrained generation can hallucinate relations or refer to objects that are not in the scene~\cite{tam_let_2024}.

\section{Language Models, VLMs, and Dialogue Services}\label{sec:server-dialogue-services}

The server does not depend on one language-model vendor. It has provider adapters for OpenAI, OpenAI API compatible (e. g., llamacpp server hosted models), Google Gemini, and local Hugging Face models. In practice, this makes the architecture usable with API models during development and with local open models when privacy, cost, or offline operation matters.

The local model choices are deliberately ordinary community models rather than a new model contribution of this thesis. Examples include a very well known and used Qwen-family models such as Qwen3.5-35B-A3B, Qwen3.5-0.8B, and Qwen3-VL-8B-Instruct~\cite{qwen_qwen35_35b_a3b_2026,qwen_qwen35_08b_2026,qwen_qwen3_vl_8b_instruct_2025}. Qwen2.5-VL and Qwen3-VL technical reports describe the broader VLM family and its image-text-to-text capabilities.\footnote{For more information, see: \url{https://qwen.ai/blog?id=qwen3.5}} For smaller multilingual text experiments, Tiny Aya Global~\cite{coherelabs_tiny_aya_global_2026} was tested thoroughly and shown promising results. The use of multilingual models is not needed though, as the system also implements automatic translation using unofficial Google Translate API\footnote{\url{https://pypi.org/project/googletrans/}} based on the currently selected system language. There are many comparable open LLMs and VLMs; the architectural point is that the server treats them as replaceable providers behind stable prompting and parsing interfaces.

The chat service converts scene memory into prompt context. It orders objects by a salience heuristic that gives extra weight to people, social attributes such as waving or looking at the robot, engagement zone, distance (these are acquired from the robot metadata), recency, and hit count. It serializes visible objects, attributes, relations, and recent captions into a compact text context. The language model is then asked to answer over that context rather than from its parametric memory alone.

Object-focused chat narrows the context further. If the user asks about a label such as \enquote{chair}, the service matches current memory objects by normalized label, orders them by salience, and includes only the relevant object records and their neighboring relations. If the matched object has few structured facts and a stored crop is available, the service can call the caption model on the crop as a fallback. This avoids a common failure mode where an object is detected and tracked, but no relation generator has said anything useful about it yet.

The caption route serves a different interaction need. It can return a quick scene description and optionally start the full detection pipeline in the background. This gives Pepper a low-latency answer for broad questions such as \enquote{what do you see}, while the more expensive detection, tracking, SoM, relation, memory, and question-generation stages can update state for later turns. The caption is also stored in scene memory with provider and model metadata.

The server also pregenerates question-answer pairs from the current scene graph. These pairs are stored in a bounded QA pool and can be exposed to the robot tablet or recognized through cached interaction paths. This is not the main dialogue method; normal chat still exists. It is a latency optimization for predictable scene questions, where an answer can be prepared immediately after perception rather than generated from scratch when the user asks. It is used on the robot side where it is saved as a QiChat dynamic concept.

\section{Scene Memory and Inspection}\label{sec:server-scene-memory}

Scene memory stores the state used by dialogue and the dashboard. It contains tracked objects, relations, captions, object crops, and Pepper person bindings. Object records include identifiers, labels, bounding boxes, attributes, first-seen and last-seen timestamps, hit counts, scan and frame identifiers, optional bearing values, optional robot distance, and optional Pepper person identifiers. Relation records are triples with subject identifier, predicate, object identifier, timestamps, and counts.

Memory is bounded by age and capacity. Memory is pruned so stale observations do not dominate the robot's answers. This matters in a physical setting. If a cup was seen five minutes ago and is no longer visible, the robot should not speak as if the cup is definitely still present. The memory timeout is configurable in the dashboard.

The memory API exposes this state as a first-class resource. Clients can read the full scene state, request a summary, fetch object crops, list objects and relations, reset memory, upsert a scene state, and manually create, update, or delete objects and relations. %In worker mode these calls are proxied to the worker memory; in in-process mode they use the pipeline memory directly. Manual editing is useful for debugging, but it also shows the intended abstraction. The system represents scene knowledge as objects and relations that can be inspected and corrected.

\section{Configuration, Worker Control, and Dashboard}\label{sec:server-worker-runtime}

Configuration changes are divided into hot updates and hard reloads. Thresholds, prompt paths, selected runtime flags, and some provider parameters can be pushed into a running worker; They can be hot-reloaded. Changes that rebuild model objects require a hard reload. The worker manager tracks process state, startup and shutdown, health checks, inflight requests, idle timeout. Theis matters mainly for the mentioned GPU allocation.

The dashboard is the developer-facing view of the same runtime. It receives WebSocket events for detections, captions, memory updates, and chat messages. It also exposes configuration panels, worker status, memory views, QA pool views, scene graph outputs, translation settings and live images.

As we can see now, the server main contribution is an integration architecture. It does not bring any new models of scene graph generation or detection, but it tries to combine strong ready-to-use components into a controllable runtime for Pepper. %detector backends produce boxes, tracking gives persistent identities, Pepper metadata adds embodied social evidence, SoM and scene graph backends turn detections into relations, memory keeps the result bounded and inspectable, and language services turn that state into dialogue.

\chapter{System Architecture and Design}\label{chap:system_architecture_rewrite}

Chapter~\ref{chap:background} introduced the methods and platform constraints that shape the thesis.
This chapter establishes the architectural level of the proposed scene-aware dialogue system: the client--server split, the flow from visual observation to scene memory, and the way that memory grounds dialogue.
Chapters~\ref{chap:server_side_rewrite} and~\ref{chap:robot_side_rewrite} then describe the server and Pepper implementations.
The code is publicly available at \url{https://github.com/JakubCiesko/pepper-ot}.

\section{Design Goals and Constraints}\label{sec:architecture-goals}

The system is shaped by Pepper's role as an embodied dialogue platform.
As discussed in Section~\ref{sec:pepper-specification}, Pepper provides the social and physical interface, but visual and language inference must run externally.
The architecture therefore has three goals: grounded speech, where claims are backed by detected objects, attributes, and relations; persistence, where observations survive beyond a single camera frame; and interaction robustness, where slow or failed model calls do not leave the robot unresponsive.

\section{Distributed Client--Server Architecture}\label{sec:architecture-client-server}

\begin{figure}[!htbp]
\centering
\includegraphics[width=1\linewidth]{pics/architecture.pdf}
\caption{High-level architecture of the proposed scene-aware dialogue system. The Pepper robot client handles user speech input, speech and tablet output, image capture, and robot metadata collection. The server exposes perception, chat, and memory services that create and use the scene representation.}
\label{fig:overall-system-architecture}
\end{figure}

The system follows the distributed architecture shown in Figure~\ref{fig:overall-system-architecture}.
Pepper acts as the embodied client: it listens through QiChat, captures images, collects robot metadata, sends requests, speaks answers, and updates the tablet.
The server owns the computationally expensive and persistent components: perception, scene graph generation, scene memory, language-model calls, configuration, and monitoring.

The split is intentionally narrow.
The Pepper client depends on stable request and response contracts, not on the active detector, VLM, LLM, or scene graph backend.
Visual requests carry images with robot metadata, while dialogue requests carry the user query and optional object focus, i. e. object label.
The server replies with captions, memory summaries, grounded answers, or updated scene state, leaving model experimentation on the side where GPU resources, worker processes, logs, and dashboard controls are available.

\section{Interaction Modes and Data Flow}\label{sec:architecture-data-flow}

The architecture supports several interaction modes because user requests do not require the same perceptual effort.
A quick look captures one image and asks for a caption while heavier updates may continue in the background; a full scan observes the room from multiple head poses and builds persistent objects, attributes, and relations.
General questions use the current scene memory without necessarily taking a new image, object-focused questions add a recognized label to narrow the context, and memory display exposes the robot's current belief state through QiChat dynamic concepts and the tablet.

\section{Perception and Scene-Graph Pipeline Design}\label{sec:architecture-perception-pipeline}

\begin{figure}[p]
\centering
\includegraphics[height=0.86\textheight]{pics/pipeline_less_detailed.pdf}
\caption{High-level perception and memory pipeline. A robot observation can produce a fast caption, detected objects, persistent identities, Set-of-Mark images, scene graph relations, pregenerated questions, and memory updates.}
\label{fig:architecture-perception-pipeline}
\end{figure}

Figure~\ref{fig:architecture-perception-pipeline} shows the perception pipeline at the design level.
The input is a robot observation: an image together with metadata about the camera, head pose, capture mode, and available robot perception signals.
One branch produces a fast caption for immediate speech; another detects objects and creates the grounding layer used by memory and dialogue.

After detection, object association connects frame-local detections to persistent memory entries.
Scene graph generation is then built over these grounded objects.
Geometric rules, RelTR, VLM-based relation generation, and robot-native person metadata can all contribute evidence.
The metadata path adds social facts that pixels alone may not expose, such as distance from Pepper, engagement, waving, or gaze.
No relation source is treated as final authority; relations are normalized, filtered, merged, and stored in scene memory.

For the VLM path, Set-of-Mark prompting follows Section~\ref{sec:set-of-mark}: persistent identifiers, labels, boxes, masks, or polygons are rendered into the image so the prompt can ask about known object instances.
The pipeline outputs updated memory, captions, object records, relations, attributes, and optionally pregenerated questions for later dialogue turns, tablet display, and the evaluation in Chapter~\ref{chap:experiment}.

\section{Scene Memory as the Central Abstraction}\label{sec:architecture-scene-memory}

Scene memory is the main abstraction between perception and dialogue.
Raw detections are tied to one image, but conversation needs stable references over time.
The memory therefore stores grounded objects, relations, captions, robot-derived person facts, and cached question-answer pairs as the authoritative representation of what the robot currently knows.

This design avoids two competing world models.
The server maintains the complete scene state because it runs perception, relation generation, and language-model context construction.
The robot mirrors only the interaction-relevant subset used by QiChat and the tablet, such as object labels, relation names, attributes, cached questions, and cached answers which are used as quick facts about the scene.

The same representation gives the language model a controlled source of grounding.
Instead of passing the whole image history into every dialogue turn, the server serializes selected objects, attributes, relations, and recent captions into a compact context, optionally narrowed for object-focused questions.
Explicit storage also makes the state inspectable: the dashboard can show current memory, the robot can display a summary.
For this reason, scene memory is a first-class component and a cornerstone of the system rather than a temporary by-product of detection.

\section{Robot Dialogue Layer}\label{sec:architecture-dialogue-layer}

The robot-side dialogue layer is deliberately not an open-ended LLM loop. It is completely deterministic and works as a traditional rule-based dialogue management system.
QiChat remains the front end that selects the system action: quick look, scan, general chat, object-focused chat, memory display, memory reset, or cached answer.
Only after this intent is known does the system call the server and, when needed, a language model.

This keeps embodied action under local control.
Speech, head motion, image capture, tablet updates, and network requests must be coordinated by the robot client; the server language model is used for grounded response generation, not for deciding which local robot API to call.
Dynamic concepts, detailed in Section~\ref{sec:client-dynamic-concepts}, connect changing scene memory with the static QiChat grammar so Pepper can recognize objects and cached questions that were not known when the topic file was written.

Turn management completes the dialogue design.
A robot action may involve an acknowledgement, motion, one or more captures, a server request, local state updates, and a spoken result.
The client therefore treats such actions as turns and prevents long-running turns from overlapping, as implemented in Section~\ref{sec:client-turn-management}.
